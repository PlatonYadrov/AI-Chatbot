# Highland AI Chat Architecture

Документ фиксирует текущее состояние репозитория и очерчивает работы, необходимые для получения полнофункционального сервиса.

## Реализованный каркас
- **Ingestion & Indexing**: директории `services/ingestion/connectors|parsers|processors` с заглушками под коннекторы (Confluence, iSpring, MIF, файловое хранилище), парсеры документов, препроцессинг, эмбеддер и индексатор.
- **Online RAG**: структуры для API-шлюза, аутентификации, rate-limiters, гибридного поиска, ре-ранжирования, генерации ответов, guardrails и кэширования.
- **Admin Portal**: заготовки для backend-API загрузки и управления метаданными, а также каталога frontend-приложения.
- **Shared**: общие библиотеки (Kafka, Redis, Qdrant, модели, телеметрия) оформлены отдельным модулем.
- **Инфраструктура**: черновые конфигурации docker-compose и сервисов (Qdrant, Kafka, Redis, Airflow, мониторинг, Postgres).
- **Документация и тесты**: подготовлены файлы под архитектуру, ранбук, OpenAPI и набор тестов.

## Необходимые доработки
### Контур ingestion
- Реализация коннекторов с авторизацией, обработкой инкрементальных обновлений, публикацией событий в Kafka и DLQ.
- Внедрение парсеров с использованием Tika/OCR, нормализацией таблиц и заметок, выделением метаданных.
- Построение процессоров для нормализации текста, дедупликации (MinHash/SimHash), извлечения метаданных, PII-редактора и чанковки.
- Разработка сервиса эмбеддингов (батчинг, GPU, кэш) и индексатора для Qdrant со стратегией версионирования и soft-delete.
- Оркестрация пайплайна через Airflow/Prefect (`scheduler.py` + DAG-и).

### Контур online RAG
- Поднятие FastAPI-шлюза с авторизацией (SSO/LDAP) и rate-limiters.
- Реализация кэшируемого эмбеддера запросов, гибридного поиска (dense+sparse), ре-ранжера и построителя промптов.
- Интеграция LLM-сервиса (DeepSeek), guardrails (entailment/PII) и сборки финального ответа.
- Настройка Redis-кэшей, Pub/Sub и механизма инвалидации.

### Административный портал
- Backend: обработка загрузок, управление метаданными, мониторинг состояний задач, экспорт отчетов.
- Frontend: компоненты для drag-and-drop, таблиц статусов, журналов и отчётности.

### Инфраструктура и эксплуатация
- Заполнение конфигураций реальными параметрами, подготовка Helm/terraform/ansible-скриптов.
- Автоматизация CI/CD (линт, тесты, деплой) в `.github/workflows/`.
- Настройка мониторинга (метрики, дашборды, алерты) и трассировки (OTel).
- Написание подробного ранбука, сценариев восстановления и SOP.

## Приоритет реализации микросервисов

1. **Ingestion-пайплайн как первый контур.** Без готового потока `source → Kafka → Qdrant` остальной стек остаётся без данных.
   - Стартовать имеет смысл с одного источника (например, Confluence) и пройти по всей цепочке: коннектор → парсер → процессоры →
     эмбеддер → индексатор.
   - На этом этапе фиксируются контракты Kafka-топиков (`raw_docs`, `parsed_docs`, `ready_for_embedding`, `embeddings`) и схемы
     payload из `shared/models.py`. Остальные источники подключаются позже, повторно используя pipeline.

2. **Взаимодействие между микросервисами ingestion.**
   - Коннекторы публикуют `DocumentRaw` в `raw_docs` и ждут ack от брокера.
   - Парсеры подписываются на `raw_docs`, сохраняют артефакты в объектное хранилище (при необходимости) и отправляют `ParsedDoc` в
     `parsed_docs`.
   - Процессоры преобразуют `ParsedDoc` в набор `ChunkReady` и кладут их в `ready_for_embedding`; тут же можно внедрить Redis-каши и
     телеметрию для измерения SLO.
   - Эмбеддер батчит `ChunkReady`, создаёт вектора и складывает `EmbeddingPoint` в `embeddings` (либо шлёт напрямую в индексатор по
     gRPC/HTTP).
   - Индексатор читает `EmbeddingPoint`, апсертает данные в Qdrant и публикует событие `index_updated` в Redis Pub/Sub.

3. **Online RAG как следующий приоритет.**
   - После того как в Qdrant есть данные, реализуется минимальный happy-path: FastAPI `gateway` → `query_embedder` → `dense_search`
     → `llm_service` → форматирование ответа.
   - Важный фокус — использовать те же модели и фильтры, что и ingestion (`shared/models.SearchFilters`), чтобы обеспечить целостность
     ACL.
   - По мере готовности добавляются `sparse_search`, `hybrid_search`, `cross_encoder_service` и guardrails.

4. **Админ-портал и вспомогательные сервисы.**
   - Backend админки должен уметь инициировать `scheduler` (HTTP) и показывать состояние очередей/тасков.
   - Frontend может начинаться с простого UI для запуска пайплайна и просмотра логов, опираясь на REST-методы backend.

5. **Инфраструктура и автоматизация.**
   - Как только первый контур готов, собираются docker-compose/Helm-манифесты для локального и dev-развёртывания.
   - На базе `.github/workflows/ci.yml` добавляются линтеры/тесты, а также smoke-тесты для пайплайна ingestion и REST API RAG.
